--------------------------------------------------------------------------------
0. 한 줄 요약
--------------------------------------------------------------------------------
주민/학생이 방치 자전거를 사진+위치로 신고 → 관리자가 승인/반려/중복 처리 →
시스템이 차량 조건 반영 최적 수거 경로를 생성 → 수거 후 재고로 등록·관리하고
대시보드에서 실적과 최적화 효과를 확인한다.

핵심 목적(기획안 1장): 신고 데이터를 공간적으로 통합하고, 수거 대상의
우선순위와 차량 이동 경로를 자동으로 계산한다.

해결하는 문제: 신고 비체계 관리, 중복 신고, 불필요한 이동거리, 처리현황
불투명, 졸업·이사 시즌 급증에 선제 대응 불가.

목표: "앱 + 연구 논문"이 한 세트로 나오는 포트폴리오.
검증 전략: NYC 311 공개데이터로 방법론 검증(완료) → 제주 데이터에 적용.


--------------------------------------------------------------------------------
1. 기술 스택 (2026-07-15 MVP 최소화 확정 — "서버는 최적화 하나만")
--------------------------------------------------------------------------------
원칙: CRUD에는 서버를 두지 않는다. 앱 ↔ Supabase 직결이 기본.

- 클라이언트 : Flutter + supabase_flutter (상태관리 Riverpod)
               로그인/신고 CRUD/사진 업로드 전부 Supabase SDK로 직접 호출.
               일반/관리자 같은 앱, profiles.role로 화면 분기.
- DB/인증/파일: Supabase — PostgreSQL + PostGIS + Auth + Storage
               권한은 RLS로 DB 레벨 강제 (별도 API 인증층 불필요)
- 중복 탐색  : PostgreSQL 함수(RPC) 하나 — ST_DWithin 반경+상태 필터.
               서버 불필요, 앱이 supabase.rpc()로 호출.
- 최적화 서버: 초미니 FastAPI — 엔드포인트 하나 (POST /optimize).
               OR-Tools CVRP 실행만 담당 (파이썬 필요한 유일한 부분).
               제약: 적재량, 작업시간, 우선순위, 필수지점, 출발/복귀.
               배포: Cloud Run 또는 Railway/Fly 무료티어.
- 이동시간   : MVP는 하버사인 근사(PoC 검증됨) → 2차에 카카오 자동차
               길찾기 API 행렬로 교체 (이때만 카카오 REST 키가 서버에 필요)
- 지도 표시  : 카카오지도 (kakao_map_plugin, JS 키)
- 길 안내    : KakaoMap 외부 앱 URL 연결 (키 불필요)
- 위치 검색  : 카카오 로컬 API — 필요해지는 시점에 추가 (MVP는 GPS+지도핑으로 충분)

구성 요약: [Flutter 앱] ↔ [Supabase] + [FastAPI /optimize 하나]
서버 코드는 파일 다섯 이내로 유지하는 것이 목표.

[보안 원칙 — 절대 준수]
- 앱에 넣어도 되는 키: Supabase anon key(RLS 전제), 카카오맵 JS 키(번들 제한).
- 금지: Supabase service_role 키, 카카오 REST 키 — 서버 환경변수에만.
- 모든 쓰기 권한은 RLS 정책으로 검증 (예: 신고 생성은 본인만, 승인은 admin만).
  (참고: 이전 DetectingMites 프로젝트의 키 하드코딩 실수를 반복하지 않는다.)

2. 사용자 역할 (기획안 2장 — 2역할로 확정)
--------------------------------------------------------------------------------
- user  (일반 유저) : 학생/지역 주민. 사진+위치로 신고, 처리 상태 확인,
                      지도에서 방치 자전거 분포 확인.
- admin (관리자)    : 운영팀. 신고 검토(승인/반려/중복), 수거 대상 선택,
                      경로 생성, 현장 수거, 완료 사진 등록, 재고 관리.
※ 이전 설계의 collector(수거팀) 역할은 admin에 통합됨.
역할은 Supabase user metadata / profiles.role 로 관리, RLS로 강제.

4. 데이터 모델 (Supabase PostgreSQL + PostGIS) — 초안
--------------------------------------------------------------------------------
profiles                       ※ Supabase auth.users 1:1
  id uuid PK (auth.users 참조), role text ('user'|'admin'),
  display_name, created_at

reports
  id uuid PK, reporter_id uuid FK,
  photo_url text, geom geometry(Point,4326), address text,
  condition text  -- '장기방치의심'|'파손'|'통행방해'|'부품분실'|'기타'
  description text,
  status text     -- 'submitted'(접수) → 'approved'(승인)|'rejected'(반려)
                  --  |'duplicate'(중복) → 'scheduled'(수거배정) → 'collected'
  duplicate_of uuid FK(reports),   -- 중복 처리 시 원본 신고
  priority int DEFAULT 0,
  reported_at, reviewed_at, collected_at, job_id FK

collection_jobs                ※ 수거 작업 (ADM-03~06)
  id uuid PK, admin_id FK, vehicle_capacity int, depot_geom, return_geom,
  work_minutes int, status ('planned'|'in_progress'|'done'),
  total_distance_m, total_duration_s, created_at

job_stops                      ※ 방문 순서 (OR-Tools 결과)
  job_id FK, seq int, report_id FK, eta, done bool, done_photo_url

bikes                          ※ 재고 (ADM-07/08)
  id uuid PK, report_id FK, collected_at,
  state text ('보관'|'수리'|'기부'|'재사용'|'폐기'), state_updated_at, note

(통계는 뷰/집계 쿼리로: 일별 신고/수거 수, 최적화 전후 거리 비교 등)

[PostGIS 활용]
- 중복 신고 탐색: ST_DWithin(geom, 신규신고, 30m) + 시간창 + 상태 필터
- 지도 분포/클러스터: 바운딩박스 질의
- 향후 핫스팟: 그리드 집계 후 Gi* (PoC 방법론)

5. 지도·경로 역할 분담 (기획안 5장)
--------------------------------------------------------------------------------
- "무엇을 어떤 순서로 방문할지" = FastAPI + OR-Tools CVRP가 푼다
  (적재량·작업시간·우선순위·필수지점·출발/복귀 제약)
- "지점 간 이동시간/거리 행렬"   = MVP: 하버사인 근사 → 2차: 카카오 길찾기 API
- "실제 길 안내"                 = KakaoMap 외부 앱 URL로 연결 (인앱 아님)
- 지도 표시                      = 카카오지도 (JS 키)

[PoC에서 검증된 교훈 — 운영 이식 시 필수]
- 지점 수요가 차량 용량 초과 → 방문 분할(예: 최대 30대/방문)
- 총수요 > 총용량 → disjunction(수요 가중 페널티)으로 이월 처리


--------------------------------------------------------------------------------
6. MVP 완료 기준 (기획안 6장 — E2E 시나리오)
--------------------------------------------------------------------------------
다음 10단계가 처음부터 끝까지 정상 작동해야 MVP 완료:
  1. 일반 유저가 사진+위치로 신고
  2. 일반 유저가 처리 상태 확인
  3. 관리자가 승인/반려/중복 처리
  4. 관리자가 수거 대상 여러 건 선택
  5. 시스템이 차량 조건 반영 최적 경로 생성
  6. 관리자가 방문 순서대로 수거
